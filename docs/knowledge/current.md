Trailnotes is a photo-by-photo hiking guide site. Each hike is an MDX guide whose route, turning points and view directions come from a GPS recording (GPX) and the EXIF data of the hiker's photos.

**The tests run on `fixtures/`, which is all invented:**

It's written by `scripts/make-fixture-guide.ts` (place, route, text and placeholder photos are all made up), with its photos in `fixtures/photos/cedar-ridge` in both stored sizes. Its shape mirrors what Strawberry Peak was, because the tests were written against that.
- `fixtures/hikes/ridgeline-loop` and `granite-saddle` are made-up drafts; `granite-saddle` exercises every pin type and section rule. They have no photo files.
- `fixtures/sample-photos` are JPEGs with real EXIF for the ingest tests.

**`content/hikes` is now a gitignored working folder** for the file store (`CONTENT_DIR` overrides it): empty until you create hikes under `pnpm dev` or run `pnpm content pull`. Under `pnpm dev` it's created if missing; anywhere else a missing folder is an error, so a plain `pnpm build` on a machine without it needs `CONTENT_DIR=fixtures/hikes` (CI does this) or `CONTENT_STORE=postgres`.

## Architecture

```
ContentStore (src/lib/store)                      one interface: list, read, save, publish, create, setTrack, history, revision, scheduleDelete, cancelDelete, remove
  ├─ local backend     <CONTENT_DIR or content/hikes>/<slug>/{index.mdx, waypoints.json, track.json?}   CONTENT_STORE unset (default)
  └─ postgres backend  tables hikes / hike_revisions, through Drizzle (src/db)       CONTENT_STORE=postgres
        ▲ every write: validateHike (zod schemas + MDX compile + no code), then a version check
        │
src/lib/content.ts ── read ──► compileGuide (server, src/lib/mdx/compile.ts) ──► /hikes/[slug], cached
/editor + /api/editor/[slug] ── getEditor() + can() ──► store.save ──► revalidatePath
scripts (ingest, gpx, content, editors) ── scripts/lib/stores.ts ──► the same store
```

- **Stack:** Next.js 16.3 App Router (breaking changes vs. older Next: read `node_modules/next/dist/docs` first; `middleware` is now `proxy`), React 19.2, Tailwind v4 with brand tokens in `src/app/globals.css` (never hardcode hex in components), zod 4, `@mdx-js/mdx` 3, Drizzle ORM 0.45 over postgres.js for the database, Supabase for sign-in and photo storage (`@supabase/ssr`; `@supabase/supabase-js` in the photo scripts), Mapbox GL 3 through react-map-gl 8, Vitest 5, pnpm 11, Node 24 in CI. The package is `"type": "module"`. Velite was removed on 2026-10-05.
- **Schemas are the single source of truth** (`src/lib/schemas.ts`), shared by the save gate, the scripts and the editor.
- **Content store** (`src/lib/store/`):
  - `types.ts` is the interface. `store.ts` (`createStore(backend)`) holds all the rules once: nothing reaches a backend without `validateHike`, every change names the version it's based on and a stale one is refused, and saves only change the **working copy**. The public site reads the **published copy**: `publish` validates the working copy again and copies it (at the version the editor saw) to the published copy; `unpublish` clears it. `status` is `published` exactly when there's a published copy; the `draft` frontmatter flag was retired on 2026-10-08 (zod drops it if an old revision still has one). The track is shared by both copies, so `pnpm gpx` on a published hike changes its public map at once. **Deleting is in two stages** (owner, 2026-10-09). `scheduleDelete` is the editor's delete: at the version last seen, it clears the published copy at once and sets the hike's `deleteAfter` to 72 hours on (`DELETE_DELAY_HOURS`). Until then the hike is an ordinary draft that can be opened and edited but not published, and `cancelDelete` takes it off the schedule (it stays a draft). `remove` deletes a hike and its history whatever its state: the purge below, tests and scripts use it. The schedule is the column `delete_after` (migration `0004_scheduled_delete`), or with files a `.delete-after` file beside the guide, outside the version hash.
  - The address `new` is reserved (`RESERVED_SLUGS` in `schemas.ts`) and refused by `validateHike`, so the scripts can't create it either.
  - Backends only read and write raw records: `local.ts` (version = hash of the files; an invalid hand-edited guide is still readable, flagged `details: null`; a `track.json` that doesn't validate is flagged `trackUnreadable` and the store refuses to save over it rather than delete it; writes to one hike are queued so two saves from the same version can't both pass) and `postgres.ts` (Drizzle over `DATABASE_URL`; version = integer column; every change is one TypeScript transaction: version check, write and history row). There's no SQL in the app: the supabase-js store and its `save_hike` / `create_hike` functions were removed on 2026-10-08 (migration `0001_drop_sql_functions`).
  - `server.ts` (`getStore()`, `server-only`) picks by `CONTENT_STORE`. It is explicit, not "is a key present", so a missing key is a loud error, and so is a mistyped value (`next.config.ts` checks `CONTENT_STORE`, `EDITOR_AUTH` and `NEXT_PUBLIC_PHOTO_STORAGE` at startup).
  - Where the published copy lives: columns `published_mdx`, `published_waypoints`, `published_details`, `published_version`, `published_at` (migration `0002_published_copy`); in files, `content/hikes/<slug>/published/{index.mdx, waypoints.json}`.
  - Pins are stored exactly as written (validated, not rewritten); the database columns are `json`, not `jsonb`, because jsonb reorders keys.
- **Rendering:** `src/lib/content.ts` reads through the store and compiles MDX on the server (`compileGuide`). `/` (the landing page), `/hikes` (the gallery) and `/hikes/[slug]` are static with `revalidate = 3600` and `dynamicParams = true`: refreshed when a guide is published or unpublished (`revalidatePath`), hourly as a safety net, and a failed refresh keeps the last good page. The site shows published copies; under `pnpm dev` it shows every guide's working copy instead, so edits appear on reload. With the file store, a missing guides folder is an error rather than "no hikes" (except under `pnpm dev`, which creates it).
- **Identity** (`src/lib/auth/`): `getEditor()` (`server.ts`) and `can()` (`can.ts`) are the only access checks, always on the server. `EDITOR_AUTH` picks the mode: unset = a fixed local owner under `pnpm dev`, nobody anywhere else; `supabase` = Google sign-in through Supabase Auth, and only users in the `editors` table count (read through Drizzle, so it needs `DATABASE_URL`); `off` = nobody. Routes: `/sign-in`, `/auth/sign-in`, `/auth/callback` (signs a non-editor straight back out), `/auth/sign-out`; `src/proxy.ts` refreshes the session for editor routes only. Outsiders get a 404 everywhere.
- **Landing page and gallery:** `/` (`src/app/(site)/page.tsx`) is the front door, built from *Trailnotes Landing.dc.html* in the design project (2026-10-09): a centred headline with two pill buttons ("Browse hikes", and "See a sample guide" to the latest published guide), a preview of that guide, three features in a row (`#features`, which the header's "Features" link points at), and a closing "Pick your next hike." band. The preview (`components/landing/GuidePreview.tsx`) is live, not a picture: the guide's first four steps beside its map in one card, inside a `HikeProvider` fed by `getHikePage`, so picking a step or a pin moves the other. The three labels pointing at it show from 1280 px up, where there's room beside the card. Where the design's sample content isn't true of the published guides it was changed: the third feature is "A photo at every turn", not "360° views" (no guide has a 360° photo yet), and the third label is "Recorded route", not "Water + exits". The site's own header and footer are kept; the design's minimal footer links to About and Contact pages that don't exist. With no published guide, the preview and the sample link are left out. Under `pnpm dev` the preview is the newest guide by date, a draft (`ridgeline-loop`). The gallery (map, filters, cards) is at `/hikes` (it was `/` until 2026-10-08). Both list hikes, so both are in `LIST_PATHS` (`src/lib/site.ts`), which the editor's routes refresh after a create, delete, publish or unpublish. The header's nav (`SiteNav`, a client component for the current-section underline) and the footer (`SiteFooter`: wordmark and a line about the site, links to the gallery and the three latest guides, the repo and licence, then the "conditions change" reminder) are on every public page; the footer reads the hike list and leaves the guide links out if the store can't be read.
- **Public pages around the guides:** app icons (`src/app/icon.svg`, drawn by hand from `components/ui/Logo.tsx`; `favicon.ico` and `apple-icon.png` are rendered from it with `pnpm icons`, so rerun that after changing the SVG), `robots.ts` and `sitemap.ts` (published hikes only; absolute links come from `src/lib/site.ts`: `NEXT_PUBLIC_SITE_URL`, else Vercel's production domain), Open Graph/Twitter cards (the cover photo is the card image), `error.tsx` and `global-error.tsx` (Next 16 passes `retry`, not `reset`), `not-found.tsx`, a skip link and a footer (`components/ui/`). `next.config.ts` sends four security headers on every response; there is no Content-Security-Policy yet (the preview evaluates compiled MDX and Mapbox needs `blob:` workers, so it has to start report-only).
- **Beside each guide's page** (`src/app/(site)/hikes/[slug]/`), both cached like the page (made at build or on first request, refreshed by the publish route with their own `revalidatePath`, and hourly):
  - `route.gpx`: the route and pins as a GPX file (`src/lib/gpx-export.ts`): the track as one `<trk>` with elevation in metres, each pin as a `<wpt>`, and no times, since the track is stored without them. Linked from the guide's header, and from the `<GpxDownload />` block where a guide places one. A draft has none, so in the editor the block's button leads nowhere until the guide is published.
  - `og.jpg`: the cover as a 1200 × 630 JPEG (about 90 KB for Strawberry Peak), which is the Open Graph and Twitter image. Made with sharp, not `next/og`, which can only produce PNG. A guide without a cover has no image and gets a text-only card.
- **Guide page extras:** JSON-LD (`Article` about a `Place`, with the trailhead's coordinates); the cover's alt text is the caption of the pin that shares its photo, else "On the … hike, region"; photos in guide sections and photo cards open in `components/hike/PhotoLightbox.tsx`, a native `<dialog>` that fills the screen. It's driven by `photo` / `openPhoto` in the hike store: stepping through photos (buttons or arrow keys) selects each pin, so the maps follow, and closing scrolls the guide to the photo left open. One per `HikeProvider`, mounted on the guide page and the landing page; 360° photos keep their own viewer.
- **Create route** (`src/app/api/editor/route.ts`, `POST`): the same guards, then `store.create`. The form behind it is `/editor/new` (`NewHikeForm.tsx`): an optional GPX is parsed in the browser with `src/lib/gpx.ts`, so only `[lng, lat, ele]` is ever sent, and `src/lib/new-hike.ts` builds the draft (details, a route map, a trailhead pin). The address `new` is reserved.
- **Save route** (`src/app/api/editor/[slug]/route.ts`), in order: editor check, same-origin, size and rate limits (`src/lib/auth/request.ts`), then the store (validation, version). It writes the working copy only, so it refreshes nothing public. Conflicts are 409, invalid content 422. `DELETE` on the same route schedules the hike for deletion (`baseVersion` in the body) behind the same guards, refreshes the public pages (it may have been published) and answers with `deleteAfter`; 409 for a stale version. `POST …/restore` takes it off the schedule. Both editor routes answer every other method with 404 too.
- **Photo routes** (`src/app/api/editor/[slug]/photos/route.ts`, behind the same guards as a save; `src/lib/photo-store.ts` is the server's side of photo storage):
  - `POST { files: [{ name, fullBytes, thumbBytes }] }` (30 at most) answers with a storage key and two upload URLs per photo. The server makes the paths (`<slug>/<NN>-<kebab name>`, numbered after everything in the hike's folder and in its pins), so a request can't name one. With Supabase the URLs are signed upload URLs (valid two hours, never replacing a file), and the browser sends the bytes straight to Supabase; the bucket itself enforces webp and 20 MB. The server asks for them **as the signed-in editor** (`sessionClient()`: their session cookie and the public key), and the bucket's policies decide: people on the editors list may add, list and delete objects in `hikes` (migration `0003_storage_editor_policies`: three policies on `storage.objects` and `public.is_editor()`, a `SECURITY DEFINER` function, because the editors table itself stays closed to browser roles). The site holds no service-role key. With no session to act as (`pnpm dev`'s local owner, with photos in the bucket) the route answers 503 with a sentence the editor shows, so a dev server can't write to the live bucket.
  - `GET` lists the folder's photos as keys, used or not.
  - `DELETE { key }` deletes a photo's two files, and is refused (409) while the key appears in the working or published copy (a pin or the cover; Strawberry Peak's cover is on no pin). History isn't checked.
  - A hike's photo folder is removed when the hike is removed for good (`src/lib/purge.ts`).
  - Under `pnpm dev` with `NEXT_PUBLIC_PHOTO_STORAGE=local`, the upload URLs point at `photos/local/[name]` (webp only, never replaces), which writes to `public/photos` and is a 404 anywhere else.
  - **Nothing is deleted when guides and photos don't belong together** (`photosBelongToStore`): a server with guides in files and photos in the live bucket can't tell whether the live site uses a photo, so both deletes are skipped or refused there.
- **Publish route** (`src/app/api/editor/[slug]/publish/route.ts`): `POST` publishes, `DELETE` unpublishes, both with `{ baseVersion }` and the same guards; then `revalidatePath` for the page and the pages that list hikes (`LIST_PATHS`), and the route fetches them itself afterwards (`after()`): from a route handler `revalidatePath` only marks a page, and the next request is still served the old copy, so that request is ours instead of a visitor's.
- **Keep-alive:** `vercel.json` runs `/api/health` daily; with the database store it reads from the database so the free-plan project doesn't pause. It reports the number of published hikes only, and answers 503 when the store can't be read (nothing watches it yet: see [todo.md](todo.md)).
- **Pins and guide sections** (`src/lib/pins.ts`): `start/turn/note/bailout` require a section and are numbered steps; if the MDX has no `<Step>` for one, `src/lib/mdx/remark-step-sections.ts` inserts a stub in route order. `viewpoint/landmark/water/ranger` are optional. The safety pins are `water/ranger/bailout`.
- **Component manifest:** `src/lib/mdx/manifest.ts` (pure zod, no React) defines every MDX component's props, title, category, snippet and whether it takes content. `src/components/mdx/registry.tsx` maps each name to its React component, and the components take their prop types from the manifest (`ManifestProps<"Name">`). Everything else reads the manifest: the prop checks, the editor's settings forms, the insert menu and MDXEditor's block descriptors.
- **Remark passes, in order** (one list, `guideRemarkPlugins` in `src/lib/mdx/plugins.ts`, used by the save gate `check.ts`, the server compile `compile.ts` and the editor preview):
  1. `remark-no-code`: refuses `import`/`export`, `{…}` expressions (comments are fine), props written as expressions, spreads, raw HTML other than `br`, `sub`, `sup`, `kbd`, `mark`, `details`, `summary` without attributes, and links or images that point anywhere but `http(s)`, `mailto`, `tel` or this site. Guides are content; compiled MDX is run as code (`new Function` in `MDXContent.tsx`), so nothing a guide contains may be code. "Is this expression only a comment" is a linear scan (`isComment`), not a regex: see Gotchas.
  2. `remark-step-sections`: stub `<Step auto>` for required pins; a `<Step>` inside a paragraph is refused.
  3. `remark-default-blocks`: `<BeforeYouGo auto />` first if the guide doesn't place it.
  4. `remark-component-props`: unknown components and props, types and ranges, no-content components, pin references.
- **Movable blocks:** "Before you go", the safety list and the step list are MDX components (`<BeforeYouGo />`, `<SafetyPoints />`, `<Steps />`). The guide's sidebar order comes from the frontmatter `sidebar` (ids in `SIDEBAR_CARDS`, `src/lib/schemas.ts`; cards in `src/components/sidebar/registry.tsx`); the mobile bar follows it.
- **Photos into pins** (`src/lib/ingest.ts`): the rules `pnpm ingest` follows, kept free of Node, the DOM and image libraries so the editor's photo upload can use the same ones: what's read from EXIF (`readPhotoMeta`: position, heading, 360° or not, and the capture time, which orders a batch and is never stored), capture order, heading fill (EXIF, else the bearing to the next photo, else unset), the size of each stored variant, key naming (`<slug>/<NN>-<name>`), one pin per photo (`pinsFromPhotos`) and the merge into existing pins along the track (`mergeWaypoints`). Each side reads the EXIF with exifr and resizes its own way (sharp in the script).
- **Track math** (`src/lib/track.ts`): projects points onto track segments, searching forward from the previous point so out-and-backs resolve by route order. The match slack scales with the distance from the track. Page mileages (`src/lib/hike.ts`) and ingest both use it.
- **Elevation profile** (`<ElevationProfile />`, `src/lib/elevation.ts`): feet against trail miles from the track, using the same mileages as the pins (`trackLine`), thinned to 500 samples at most (lowest and highest of each stretch, so a summit survives). The page sends it to the browser as `profile` in the hike store, next to `route`. The line is an SVG stretched to the block; pins, labels and the hover readout are HTML placed in percent, so nothing is measured. It shares the selection with the maps: the active pin is marked, and choosing a pin selects it everywhere and scrolls to its section. A hike with no track gets a one-line note instead.
- **Maps:** `TrailMap` → lazy `MapboxTrailMap`, with `SketchMap` (SVG) as the base layer and fallback. Maps mount only near the viewport and use a pool (`reuseMaps`) to stay under the browser's WebGL context limit. Pins are memoised `WaypointMarker`s.
- **Photos:** Supabase Storage is the source of truth: `<slug>/<NN>-<name>.{full,thumb}.webp`, with all metadata stripped. The bucket `hikes` is public, takes `image/webp` only, 20 MB a file, and has no storage policies (checked 2026-10-08), until migration `0003`, which lets signed-in editors add, list and delete (the service-role key, used by the scripts, bypasses policies as before). Photos get there from the editor's Pins view or `pnpm ingest`. `public/photos` is a gitignored, dev-only backend (`NEXT_PUBLIC_PHOTO_STORAGE=local`). Production builds refuse it (guard in `next.config.ts`).
- **Editor** (`/editor`, `src/components/editor/`): open to whoever `getEditor()`/`can()` allow (the local owner under `pnpm dev`; on the live site, editors signed in with Google).
  - `Editor.tsx` is the shell: it holds the guide (MDX + pins JSON), autosaves after 1.5 s through the store, and switches between five views of the same document (Write, Details, Pins, Advanced, History). Each save sends the version it was based on; a stale one shows a conflict banner and writes nothing. Saves go one at a time: one asked for while another is on its way waits, then sends the newest text with the version just received. Leaving with unsaved text asks first (`beforeunload`).
  - **Write** (default, `write/WriteView.tsx`): MDXEditor on the body only. Every manifest component is a live block rendering the real component inside a `HikeProvider`; a block's own text (a Step's notes) is a nested editor inside it; the selected block renders its generated `SettingsForm` into the settings column through a portal. `mdx-editor-config.ts` holds the shared plugin setup (also used by the round-trip test). Above the document, `write/GeneratedSections.tsx` lists the required pins with no written `<Step>` (found by running `remark-step-sections` itself, `write/missing-sections.ts`); "Write this section" inserts an empty `<Step>` at the place the page shows it and remounts the view. If MDXEditor reports that it can't parse the guide, the view replaces itself with a notice and a button to Advanced (see Gotchas).
  - **Moving a block** (since 2026-10-09): a selected block's settings have "Move up" and "Move down", which swap it with its neighbour in the document (a paragraph, a heading or another block) by moving its Lexical node in MDXEditor's root editor (`useNestedEditorContext`; `lexical` itself isn't a dependency, so the node's own methods are used). There's no drag and drop. In Advanced, blocks are moved by moving their text.
  - **Insert menu** (`InsertMenu.tsx`): every block has an icon from `lucide-react` (added 2026-10-09, the site's only icon library), set in `componentIcons` in `components/mdx/icons.ts` (its own file, so components can read it without importing the registry that imports them); the type there fails for a component without one. The same icon is in the header of the block's frame on the page (`ui/Frame.tsx`, `icon` prop), sidebar cards included.
  - **Details** (`DetailsForm.tsx`): a form generated from `frontmatterSchema` (labels are the schema's `.describe()`); each change rewrites one frontmatter entry with `src/lib/frontmatter.ts`, leaving the rest of the YAML as written. A frontmatter with a YAML error is shown as the error (`yamlProblems`) instead of a form, and Publish says why it can't; `setDetail` throws rather than rewrite YAML it can't read. `frontmatter.ts` is also the one home of the frontmatter regex and `blankFrontmatter`.
  - **Pins** (`pins/PinsView.tsx`, `pins/PinMap.tsx`): the pins on an interactive map (drag to move, snapping onto the track within about 80 m; drag the yellow handle to aim the photo direction; add by clicking), a list in route order and a form per pin. All edits are pure functions over the pins JSON as written (`pins/pin-ops.ts`): they keep fields and their order, renumber `order` in steps of 10, slot a new pin in by trail mileage, and rename a pin together with the blocks that point at it (however the reference is written: either quote, spaces around `=`, or `{"id"}`). The form keeps an empty label or title, or an out-of-range number, to itself until it's a value the pins can hold, so the pins JSON is never invalid halfway through typing.
  - **Photos in the Pins view** (`pins/PhotoPanel.tsx`; since 2026-10-08 no CLI is needed). "Add photos", or files dropped anywhere on the view, go through four steps, shown per file (processing, uploading with a percentage, then pinned, unplaced, already added, or failed with Retry):
    1. `pins/process-photo.ts`, in the browser: EXIF with exifr, then both webp variants drawn on a canvas at the sizes `src/lib/ingest.ts` gives. Re-encoding drops all metadata, so only pixels are uploaded; position and heading travel as the pin, and the capture time stays in the tab. Where the canvas can't encode webp (Safari, so every iPhone) `@jsquash/webp` (WASM, loaded only then) does it. A full-size 360° photo is capped at 5792 × 2896, the largest canvas iOS draws.
    2. `pins/photo-upload.ts` asks the photo route where to upload and PUTs each file there with `XMLHttpRequest` (for progress). There's still no Supabase client in the browser.
    3. `pins/photo-pins.ts` (`addPhotoPins`) makes the pins with the shared ingest rules: capture order, heading from EXIF or guessed from the next photo, snapped and slotted in along the track by `mergeWaypoints`. New pins are `turn` pins labelled and titled "Photo NN" (the first photo of a hike with no pins is its trailhead). The result is saved by the normal autosave.
    4. A guessed direction shows "check direction" in the list until the pin is aimed.
  - **Unplaced photos** are the stored photos that neither the pins JSON nor the guide's text (its `cover:`) mentions (`mentionsPhoto`, `src/lib/storage.ts`): photos with no GPS, and photos taken off a pin. They're listed with a thumbnail and can be dragged onto the map, placed with a click ("Place"), picked in a pin's Photo field, or deleted. Delete is the only thing in the editor that removes photo files, and the server refuses it while the saved guide or the published copy still uses the photo, so right after taking a photo off a pin it has to wait for the autosave.
  - Not handled: a failed upload can leave one of a photo's two files behind (it shows in Unplaced with a broken thumbnail; delete it there), and a photo already stored under the same file name is skipped rather than replaced.
  - **Advanced** (`AdvancedView.tsx`): CodeMirror for the raw Markdown and pins JSON, a live preview compiled in the browser with the same remark passes, and the settings column for the component under the cursor or clicked in the preview (`jsx-source.ts` rewrites only the opening tag; `remark-source-markers.ts` makes preview blocks selectable). Layout per design 3a.
  - **History** (`HistoryView.tsx`): every saved version, newest first (the latest 100), with who saved it and a preview; "Restore this version" loads it into the editor, where autosave saves it as the newest version (nothing is rewritten, and a stale tab still conflicts). Read-only routes `GET /api/editor/[slug]/history` and `/history/[version]`, editors only. Guides in files have no history (git keeps it), so under the local store the view says so.
  - **Publishing:** the badge says Draft, Published, or "Published · changes not live" (the working copy differs from the published one). "Publish" / "Publish changes" wait until everything is saved, then publish that version; "Unpublish" asks first. A save never changes the public page.
  - **Deleting a hike** is at the end of the Details view (`DeleteDraft.tsx`, "Delete this hike"), after a second click and only once everything is saved. The text says what happens: deleting takes 72 hours, a published page comes down straight away, and until the time is up the hike can be restored. A deleted hike shows a banner with "Restore this hike" and how long is left, its badge says Deleted, Publish is off, and the hike list shows "Deleted · removed in about 3 days". It's hidden from every public page, `pnpm dev` included.
  - **Removal for good** (`purgeExpiredHikes`, `src/lib/purge.ts`) happens when an editor opens the hike list (`/editor`) after a hike's time is up: its photos first, then the guide and its history. It runs on an editor's visit, not on a timer, because photo files can only be deleted as a signed-in editor (the server holds no key of its own) and a cron job has nobody to act as. The hike is already unpublished, so nothing public depends on when it runs. If the photos can't be removed, the hike is kept for the next visit.
  - `writtenProps` (`jsx-source.ts`) is the one rule for which props get written (defaults and unticked optional checkboxes are left out), used by both the Markdown tag writer and the Write view.

## Live setup: sign-in and the database

How the live site was set up (2026-10-05, database access moved to Drizzle on 2026-10-08). These are the steps to repeat for a new environment, or to add an editor.

1. **Google sign-in client** (Google Cloud Console → APIs & Services). Consent screen: External, left in **Testing**, with each editor's Google address under Test users (in Testing nobody else can sign in at all; a new editor who isn't a test user gets Google's own error page before ours). OAuth client, type Web application: JavaScript origins `https://trail-notes-amber.vercel.app` and `http://localhost:3100`; redirect URI `https://fstcgdirhssuaevgxptv.supabase.co/auth/v1/callback` (Google returns to Supabase, Supabase to the site).
2. **Supabase** → Authentication: enable the Google provider with that client's ID and secret. URL Configuration: Site URL `https://trail-notes-amber.vercel.app`; redirect URLs `https://trail-notes-amber.vercel.app/auth/callback` and `http://localhost:3100/auth/callback`.
3. **An editor:** with sign-ups on, they sign in once (they land on "That Google account isn't on the editors list": the account now exists), then `pnpm editors add <email> [--role owner]`. Turn **"Allow new users to sign up" off** again afterwards. An account that isn't on the list can do nothing either way; closing sign-ups keeps strangers out of the user list.
4. **Vercel → Environment Variables (Production):** `DATABASE_URL` (Supabase → Connect → Transaction pooler, port 6543; Sensitive: it is the database owner's password and must never get a `NEXT_PUBLIC_` name), `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `CONTENT_STORE=postgres`, `EDITOR_AUTH=supabase`. Variables apply to new deployments only. To try sign-in on the Mac first, put `EDITOR_AUTH=supabase` in `.env.local`.

Verified on the live site:

- 2026-10-06, by the owner: Google sign-in reaches the editor; saves from the live editor are in `hike_revisions` under the owner's account; the public page picked up a change without a deploy (the first request after it was served `STALE`, the next had the change).
- 2026-10-08, signed out: the guide page and gallery are 200, `/api/health` says `"store":"postgres"`, and `/editor`, `/editor/new` and the editor's API are 404.
- Before any of it (2026-10-05, a local production server in `EDITOR_AUTH=supabase` mode): a forged session cookie gets a 404, and `/auth/sign-in` redirects to Supabase with the verifier cookies set and `/auth/callback` as the return address.

What follows from this setup:

- **The database is the only copy of the guides.** `pnpm content pull` writes them to `content/hikes` on this machine (gitignored) when you want them as files, and `pnpm content seed` copies files to the database (refusing to overwrite a stored guide that differs unless `--force`; a seed doesn't refresh the live page). There is no backup yet: [todo.md](todo.md).
- **`pnpm ingest` and `pnpm gpx` write to files** unless given `--guides postgres`. `pnpm photos check` reads the repo's guides, so it won't notice a photo used only by a guide edited live.
- **A build reads the guides from the database**, so a missing `DATABASE_URL` or a paused project fails the build (the previous deployment stays live).
- **Every autosave is a row in `hike_revisions`.** Fine at this size; pruning is a later job.
- **The save rate limit is per server instance** (60 a minute per editor): it stops a runaway tab, not an attacker. The protection is that only listed editors can save.
- **Session cookies are `HttpOnly`** (not the library default; no browser code reads them). If sign-in completes but `/editor` is still a 404, check that `sb-…-auth-token` cookies are set after the callback.
- **Supabase links a Google sign-in to an existing account by email.** Step 3 creates accounts by signing in, so this is only relevant if a user is ever created by hand in the dashboard.

## Decisions (and why)

- **Commit straight to `main`.** It's the owner's choice, so CI and a local `pnpm build` are the safety net.
- **Pins come from the GPX, photos illustrate them.** Owner, 2026-10-01: not every photo becomes a node. Use one photo per stretch of trail, and no two pins showing the same view. Several photos per point is planned for v3/v4.
- **Timestamps stay private.** `track.json` keeps only `[lng, lat, ele]`, and pins have no capture time: `pnpm ingest` uses it to order the photos and doesn't store it, and the pin schema has no such field, so one left in a stored pin is dropped when the pins are read. (Until 2026-10-07 pins carried `takenAt` and it reached the public page. The stored guides were cleaned that day; old `hike_revisions` rows and the repo's git history still hold it: see [todo.md](todo.md).) Pace and stop analysis uses the local GPX; only derived facts (grades, "pace drops 3–4×") go into published text.
- **A theme is the values in `globals.css`, not the token names.** The names (`forest`, `bark`, `paper`, `ochre`, `graphite`) come from the paper theme; under Fresh Green they hold Pine, Slate, Page, Sunny and Ink (the comments in `globals.css` give the design's names). `forest-deep` (the primary button's hover, from the landing design) was added on 2026-10-09. Pin colours are fixed across themes, except the trailhead (the primary colour); the note pin keeps its brown, because the design has no note pin and slate would look like the landmark pin. Three places can't read the tokens and repeat the hex values: `src/app/icon.svg` (then `pnpm icons`), `global-error.tsx` and `scripts/make-icons.ts`.
- **What the end-to-end tests can't reach.** Google sign-in needs a real account, and accounts are never created from a session or CI, so the signed-in editor on the live site (and the database behind it) stays a manual check: [todo.md](todo.md). The E2E editor is the dev-mode local owner on files; the store's database side is covered by the contract tests.
- **Accessibility baseline (2026-10-08).** axe (WCAG 2.2 AA plus best-practice rules) finds nothing on the gallery, the Strawberry Peak page (both at 1280 and 390 px wide), the sign-in page, the editor's hike list and new-hike form, and the five editor views. Lighthouse on a local production build:

  | Page | Performance | Accessibility | Best practices | SEO |
  | --- | --- | --- | --- | --- |
  | Gallery, phone | 76 (LCP 6.5 s) | 100 | 100 | 100 |
  | Gallery, desktop | 100 | 100 | 100 | 100 |
  | Guide, phone | 86 (LCP 4.2 s) | 100 | 100 | 100 |
  | Guide, desktop | 99 | 100 | 96 | 100 |

  The 96 is Mapbox's 403 for terrain tiles on `localhost` (the token is URL-restricted). Phone performance is Lighthouse's throttled 4G, and the slow paint is the cover photo; it wasn't tuned. Known and left: pins that sit on top of each other on a map can't each be a 24 px target (`granite-saddle` has some), which WCAG allows because the step list selects the same pins; the rest is in [todo.md](todo.md).
- **Turn pins use dark ink.** White on the turn colour was 3.27:1; `PIN_STYLES[*].ink` sets the glyph colour per type so each is at least 4.5:1.
- **Scroll performance (2026-09-30):** measured on a production build in headless Chrome: about 3% dropped frames and about 16 ms p95 scroll latency. An IntersectionObserver scrollspy, mount hysteresis and deferred map camera moves showed no measurable gain, so they were dropped. Reproduce on the reported page before optimising again.

## Gotchas

- **Next 16.3 evaluates `next.config.ts` in a child process** whose argv lacks `dev`. Detect dev with `process.env.NODE_ENV === "development"`.
- **A regex is the wrong tool for "is this only comments".** Until 2026-10-06 the no-code rule used `/^\s*(\/\*[\s\S]*?\*\/\s*)*$/`: backtracking let `{/* a */ code /* b */}` through as one comment (the code then ran during page render), and a run of `/**/` took exponential time. `isComment` scans instead, and the hostile inputs are in `component-props.test.ts`. Anything added to the gate should get the same treatment: a test that tries to smuggle code past it.
- **MDXEditor's stylesheet can load after `globals.css`.** Its theme variables are set on `.mdxeditor` (one class), so ours are written with the class doubled (`.write-editor.write-editor`). Until 2026-10-08 they were single, lost to load order, and the Write toolbar showed MDXEditor's default blue and grey.
- **The Write view can't show everything the gate accepts.** MDXEditor has no image, code-block, reference-link or footnote support here; when it meets one it reports to `onError`, renders the guide only up to that point and stops reporting edits. `WriteView` therefore steps aside on any `onError`. Don't turn that back into a console message.
- **Two secrets reach past row-level security:** `DATABASE_URL` (the database owner's connection: the site, and the scripts on the owner's Mac) and the Supabase service-role key (`SUPABASE_SERVICE_ROLE_KEY`: only the photo scripts on the owner's Mac, for Storage uploads; the site doesn't read it, photo uploads included, so it can be removed from Vercel). The app reaches the database only through `getDatabase()` in `src/lib/store/server.ts` (marked `server-only`), used by the store and by `auth/server.ts` for the editors lookup. Neither secret is ever entered into a dashboard or tool from a coding session; the owner does that.
- **Never create accounts in the real Supabase project from a session**, even test ones. Sign-in can therefore only be verified by the owner; what's unverified is listed in [todo.md](todo.md).
- **MDXEditor writes a trailing space as `&#x20;`.** `WriteView` strips it before the text is saved.
- **MDXEditor only commits a block's nested text on blur.** `WriteView` asks the nested field to commit 500 ms after a keystroke (dispatching `NESTED_EDITOR_UPDATED_COMMAND` to the field's Lexical editor, found on the element as `__lexicalEditor`), otherwise autosave misses text still being typed. It listens to key/paste events, not `input`: Lexical cancels `beforeinput`, so `input` never fires.
- **MDXEditor deletes a whole block on Backspace in its empty text field.** `WriteView` swallows that keystroke; blocks are removed with the Remove button.
- **Maps: the Mapbox layer stays `invisible` until it has painted** (`TrailMap.tsx`). Otherwise, while tiles are loading or refused, Mapbox's pins show on top of the sketch map's pins and every pin appears twice.
- **Stage files explicitly when committing.** `git add -A` once swept an editor autosave of the owner's into a commit; the dev server may be saving while a session works.
- **`DATABASE_URL` must be Supabase's transaction pooler** (port 6543), with prepared statements off (`src/db/client.ts`). The direct address is IPv6-only on the free plan, which Vercel can't reach, and the pooler doesn't keep prepared statements between transactions. It holds the database password: server and scripts only, a Sensitive variable in Vercel, entered by the owner.
- **Applying a migration to the live database:** `pnpm db:migrate` on the owner's Mac, where `.env.local` holds `DATABASE_URL` (since 2026-10-08; `0001` and `0002` were applied this way). A session without it applies the generated SQL with the Supabase connector (`apply_migration`) and, in the same call, inserts its row into `drizzle.__drizzle_migrations` (sha256 of the file and the journal's `when`), which is what `pnpm db:migrate` does. Either way, apply it before pushing the code that needs it, and check that the code already live still works on the migrated tables.
- **Postgres `jsonb` reorders object keys.** Use `json` for anything that should read back as written (pins, track).
- **`tsx` ran scripts as CommonJS until the package became `"type": "module"`;** the MDX compiler's dependencies are ESM-only and can't be `require`d.
- **Next generates the `PageProps`/`LayoutProps`/`RouteContext` globals.** Run `next typegen` before `tsc` on a fresh checkout (`pnpm typecheck` does this).
- **Phones don't get the sketch map on purpose.** An outside review reported it on 2026-10-08; there is no width rule in the code, and on 2026-10-09 the live guide drew Mapbox in real Chrome at 390 px and with iPhone 14 and Pixel 7 emulation. A page in a hidden or background tab never mounts Mapbox (the in-app browser pane does this too), which is the likely source of the report. The one deliberate sketch on a phone is the thumbnail in the collapsed "Map, safety & steps" bar.
- **Only one `next dev` per folder.** Next 16 refuses a second one. Orphaned servers from earlier sessions have been found on ports 3100/3101.
- **The in-app browser pane can't render while hidden.** No screenshots, and Mapbox doesn't initialise. For one-off visual checks and profiling (axe, Lighthouse), use `playwright-core` with system Chrome from the session scratchpad; the repo itself only has `@playwright/test`, for `pnpm e2e`.
- **Mapbox:** the token is URL-restricted, so some tiles return 403 on `localhost`. Every map registers non-passive `wheel`/`touchmove` listeners (Mapbox internals, even with `interactive: false`).
- **Checking the Safari encoder without Safari:** in Chromium, replace `OffscreenCanvas.prototype.convertToBlob` with one that returns a PNG before adding a photo; `process-photo.ts` then takes the WASM path. Done on 2026-10-08 under `next dev` (the `.wasm` loads from `/_next/static/media`, and the production build emits it too). A real iPhone hasn't been tried: [todo.md](todo.md).
- **`.claude/launch.json` has `dev-local-photos`:** the dev server on 3210 with guides in files and photos on disk, for trying uploads from a session without touching the bucket. Plain `pnpm dev` follows `.env.local`: with photos in the bucket and no sign-in, uploads are refused with a message saying which two settings allow them.
- **iPhone photos:** files dragged out of Photos are tiny previews (`…_4_5005_c.jpeg`, 360–1024 px). Use File → Export, or the original HEIC. Convert HEIC with `sips -s format jpeg` (keeps GPS and heading, writes upright pixels with a normal orientation tag). sharp's prebuilt binary can't decode HEIC.
- **A perceptual hash (dHash) doesn't detect "same vista" duplicates** when the framing differs. Compare heading and content.
- **Structural typing won't catch a manifest prop that a component ignores.** Components take their prop types from the manifest to keep one definition, but nothing forces them to use every prop.
- **`propFields` reads `z.toJSONSchema(..., { io: "input" })`.** Custom `.meta()` keys (`input`, `internal`) come through as JSON Schema keys; `.describe()` becomes `description`.
